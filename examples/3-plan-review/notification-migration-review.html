What the plan builds

plan.md sections 2 to 5

What it proposes. Replace the 5-minute cron poll with change data capture. Debezium streams each change to orders into Kafka. A new Go service, notifier, sends the notifications (1, 4). The plan rejects an outbox for now because it touches all 14 write paths. It rejects LISTEN/NOTIFY because it is not durable (3).

Scroll sideways to see the whole flow.
  1. Each change to orders goes into the WAL. The slot keeps it for Debezium.
  2. Debezium publishes one event for each change, keyed by order_id.
  3. notifier keeps the 4 notifiable statuses and builds the key.
  4. SET NX writes the key for 72 h. If the key exists, notifier skips.
  5. notifier calls the provider, then commits the offset. After 5 failures, the event goes to the DLQ.
  6. cron polls until phase 4. From phase 0, it reads the same Redis keys.
